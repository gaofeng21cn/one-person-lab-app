## OPL App 把一次问答变成持续工作

AI 已经很擅长回答问题、生成文字和修改文件。真正困难的是把这些能力放进一项会持续数天、数周甚至数月的正式工作。

一篇论文会经历材料整理、研究问题收敛、分析、作图、写作、审阅和修订；一份基金申请会反复调整创新点、技术路线和论证；一套演示要让数据、故事线、视觉和导出结果彼此一致；一本书更需要跨章节保持结构、风格和事实连续。

在这些工作里，用户需要一套贯穿全程的答案：

- 我现在应该从哪里开始？
- 当前成果由哪些材料、分析和审阅支持？
- 工作推进到了哪里，下一步可以自动继续还是需要我决定？
- 离开几天后回来，是否还能接住之前的上下文？
- 换到浏览器、服务器或云端时，是否仍在同一条工作线上？

OPL App 是 One Person Lab 面向用户的专业工作台：让目标、对话、材料、阶段、产物、审阅、回执和下一步形成一条可以继续的工作线。

## 设计一：从工作目的开始

用户打开 OPL App，首先表达“我要完成什么”，系统随后选择合适的专业能力与工作环境。内部工具、打包形态和运行方式留在系统背后。

首页入口来自当前安装并启用的能力，以及用户选择的快捷方式。例如，科研能力帮助用户从问题、材料和数据走向分析与论文；基金能力支持选题、论证和申请书；视觉能力支持图表和演示；书稿能力支持章节组织与修订。这些是工作目的的例子，不是固定产品清单。

App 根据实际可用能力动态展示入口。无论能力来自 OPL 官方还是社区与第三方扩展，新增或移除后入口都会随之变化；用户也可以自主决定哪些快捷入口出现在首页。这样的设计有两个好处：新用户可以直接从工作目的开始，熟练用户可以自由组合工作台。产品可以不断接纳新的专业能力，首屏始终只回答一个问题：你今天要完成什么？

## 设计二：成果必须带着来路

正式知识工作的结果需要同时包含成果与来路。一个结论、一张图、一页演示或一个章节，能够回到它所依赖的材料、过程和审阅，才值得被继续使用。

OPL App 把工作表达为一条可以复查的链：

```text
目标 -> 材料与资源 -> 阶段推进 -> 产物 -> 审阅与检查 -> 回执 -> 下一步
```

“结果有来路”意味着优先呈现与判断有关的信息：当前产物在哪里，哪些内容已经检查，哪里仍有质量债，下一步是继续修订、补充材料、等待资源，还是由人作决定。围绕日常工作，用户可以通过“运行状态”聚焦正在推进的任务与阶段进度，通过“资料空间”集中浏览和预览跨项目的交付物与工作文件；路径、标识、原始回执和运行细节则在排查问题时进入诊断层。

这条原则让用户既能判断最终文件是否可信，也能在首屏聚焦真正要做的事；完整内部证据则按需展开。

OPL App 负责把已有事实翻译成用户能采取行动的状态，而不是自己复制一套状态。运行进展来自 OPL Base，专业能力说明自己的可用性，研究、基金、视觉和书稿质量来自对应专业 Agent 与人类负责人。界面说明“发生了什么”和“下一步是什么”，就绪结论仍由真正负责的人与 Agent 给出。

## 设计三：状态必须指向行动

复杂产品很容易把设置页变成内部结构目录：运行环境、集成、技能、缓存、路径和诊断信息各占一栏。这样的界面看似完整，却把理解系统的成本转嫁给用户。

OPL App 采用相反的组织方式。设置首先围绕用户要做的决定：

- 当前环境是否可以开始工作，需要我做什么？
- 宿主底座、运行基座或已安装软件是否需要安装、更新或修复？
- 哪些能力已可用，哪些显示在首页，各自需要怎样的配置？
- 浏览器访问、远程连接、个人资料库或外部账号是否需要授权？
- 哪些数据由本机持有，清理或迁移会影响什么？

无论安装了多少软件和扩展，持久配置都按用户任务归入既有的统一设置分区，不因能力来源不同而衍生出互不相通的顶层菜单。默认层只显示目的、状态、影响、生效时机和主动作，并统一纳入全局设置搜索与从软件中心一键直达的路径；标识、路径、缓存和底层运行记录折叠到“高级诊断”，供需要排障的人按需展开。

这种信息架构建立了一条稳定规则：**正常状态保持安静，异常状态说清影响，所有状态都给出合法下一步。** 普通用户也能清楚判断该继续工作、等待后台完成、批准资源，还是进入修复。

## 设计四：工作位置变化，工作语言保持连续

OPL App 是本地优先的。用户可以先在自己的设备上选择工作目录，让敏感材料、早期草稿和个人项目留在自己的环境里。工作位置变化时，用户面对的是几种并列载体，而不是必须逐级迁移的路径：

```text
同一套 OPL 产品语言
  |-- 本机工作台：保留个人控制与敏感材料
  |-- 浏览器工作台：从其他设备继续同一项工作
  `-- 在线 Workspace：按需获得协作与远端资源
```

手机和其他终端可以通过浏览器或远程连接继续访问本机工作台；消息入口只负责传递内容，不创建第二套任务与会话历史。如果系统无法确认两个入口是否对应同一项工作，就保留原入口，不隐藏或误合并任务。

项目、任务、阶段、产物、审阅、阻塞、证据和下一步组成一套连续的工作语言。不同载体不必在每个细节上完全相同，但都应让用户理解自己正在做什么、成果在哪里、接下来由谁负责。

## 设计五：极薄底座、平权生态与无感演进

传统桌面软件把界面、能力和更新捆成一整块：每增加一个功能，用户就多一层菜单；每修一个问题，就要重新下载并覆盖整个安装包。OPL App 选择另一种产品形态——**一个极薄、稳定、极少需要重装的宿主底座，加上一组来源平权、按需组合、界面一致、持续自动演进的软件与插件生态。**

### 安装包只是起步载体，日常靠组件独立演进

标准版便于轻装起步，完整版便于离线预装，但两者都是首次安装的便捷载体，而不是日常更新的唯一途径。完成安装后，宿主底座保持稳定克制，兼容扩展、运行基座与已安装软件各自独立演进，在后台安静完成检查与更新。

在更新体验上，产品追求明确而不打扰：更新页提供统一的一键检查与一键更新全部；后台准备就绪后，主界面仅以不遮挡内容的轻量入口提示按需刷新或单次重启生效。纯界面扩展朝细粒度独立演进与无感轻刷新推进；若某次更新后的扩展在启动期出现异常，系统自动隔离故障并回退到内置稳定基线，保住核心对话与工作台可用，而不是把用户留在白屏或无解报错中。

### 零认知负担的软件中心与全来源平权

软件中心不是系统架构图，而是面向用户的统一目录，只回答四个日常问题：有哪些软件可用、我已经装了什么、如何开始使用或配置、哪些需要更新或修复。

首页按用户意图组织（如智能体、应用、效率扩展、连接通道），让 OPL 官方软件、社区与第三方扩展以及本机工具适用完全一致的发现、安装、启停、更新、安装记录与异常聚合规则。维护来源作为信任标识与筛选视角透明呈现，不制造“二等公民”或第二套操作流程；底层打包规格与安装器细节退居软件详情，依赖性的运行组件独立分层维护，避免把技术名词和系统依赖混进日常软件选择。每款软件所需的目录访问、外部账号、网络或运行方式，在安装前与详情页提前明示。

### 开放扩展如何守住一致体验

生态越开放，界面秩序越重要。为了避免插件各自为政、拖垮体验，所有接入 OPL App 的扩展按耦合度从低到高遵循三层递进方式，共享同一套视觉语言、明暗主题、多语言、全局搜索与真实状态回读：

| 接入层级 | 适用场景 | 用户体验与安全边界 |
| --- | --- | --- |
| 声明式配置 | 通道接入、服务开关与常规参数配置 | 按统一表单规范落入既有设置分区，标明生效时机并在提交后回读真实状态，不私建顶层导航 |
| 共享原语工作面 | 运行状态、资料空间、专项设置卡片等高频交互界面 | 复用统一设计原语与主题体系，包裹在独立错误隔离边界内；单个扩展异常自动降级隔离，不影响主工作台 |
| 沙箱协作工作台 | 复杂审阅看板、专业编辑或多步骤领域应用 | 在独立沙箱中运行，自动延续宿主主题、字号、语言、当前线程、权限与授权回环 |

这种约束把自由留给专业能力本身，把一致性还给用户：开放生态可以持续长出新能力，用户面对的始终是同一款克制、连贯、可预测的专业工作台。具体接入规范与演进路线由 [OPL App 插件界面与设置标准](https://github.com/gaofeng21cn/one-person-lab-app/blob/main/docs/product/gui/plugin-ui-and-settings-standard.md) 统一维护。

## 一个完整场景：从本机研究到团队审阅

设想一位研究者准备一篇需要重新分析数据的论文。

**从目标开始。** 她在本机打开 OPL App，选择自己的项目目录和“科研”入口，用普通语言说明研究问题、数据位置和希望形成的交付物。App 将任务交给 MAS，由 OPL 与 MAS 协同组织所需模型、方法和工具。

**让过程可见。** MAS 围绕问题、数据、分析、图表、论断和稿件推进。App 在运行状态与资料空间中持续呈现当前阶段、最新产物、需要补充的材料和等待她决定的问题。她可以打开结果，也可以回到支持结果的材料和审阅意见。

**在正确的时刻让人判断。** 如果分析已经形成可消费的增量，但某张图仍需重画，工作可以带着清楚标注的质量债继续；如果要声称结果达到投稿标准，则必须回到 MAS 的质量门和负责人确认。App 准确区分“有进展”与“已就绪”。

**延展工作位置。** 当本机资源不足时，她可以批准使用服务器或云端资源；需要合作者参与时，可以在浏览器或 Workspace 中继续。项目仍以相同方式呈现任务、产物、审阅和下一步，而资源、账号和组织策略留在对应管理面。

**把下一轮接住。** 一周后回来，她不必重新折腾安装包或环境，后台静默维护让底座与插件平稳保持可用；她直接看到当前稿件、最近一次审阅、未关闭的问题和可以继续的动作。产品为专业判断准备材料、上下文和清楚的交接点，最终学术判断仍由她作出。

这个场景也适用于基金、演示和书稿：专业内容不同，可信工作的结构相同。

## 四层产品，一套连续体验

OPL 把运行基础、用户工作台、专业能力和在线服务组织成四层产品。用户看到的是一套连续体验，每一层都由明确的产品负责：

| 对象 | 用户应如何理解 |
| --- | --- |
| OPL Base | 后台运行基础，负责让任务、阶段、专业能力和证据可靠工作 |
| OPL App | 极薄稳定的用户工作台宿主，负责统一入口、插件交互秩序、状态翻译与产品体验 |
| OPL Packages | 可安装和独立更新的专业智能体、能力、扩展与工作流，决定“能完成哪类专业工作” |
| OPL Cloud | 在线工作空间、资源连接、协作与服务治理，让工作可以跨越本机继续推进 |

具体执行工具、工作流配置、辅助扩展和底层集成都归入这四层产品，同时通过统一软件中心与扩展标准平等接纳外部生态软件。用户数据与产物拥有独立的存储、保留和清理边界；软件底座、扩展插件与在线服务各自按照适合的交付方式持续更新。

这个模型让产品边界更容易理解：Base 负责运行，App 负责工作体验与一致秩序，Packages 与开放插件负责专业能力，Cloud 负责在线工作与治理。界面汇总它们的真实状态，不要求用户理解多套运行器、安装器、状态来源与恢复机制。

## OPL Agent Apps：按需协作界面与可延续知识

在统一底座与一致界面秩序之上，OPL Agent Apps（OPL Agent 原生应用）进一步把 Agent 主导执行与人的专业判断组织为同一条工作线。Agent 应能直接调用能力、读取状态并继续工作；需要比较、编辑、审阅或决定时，OPL MiniApp 提供按需出现的协作界面。它沿用已有能力的安装、运行和权限机制，让界面成为当前工作的延伸。

用户从当前任务进入时，视图沿用已登记的工作区和任务身份，先呈现已有进度、可用产物、待决定事项和下一步；已形成的中间成果可以继续使用，领域质量待办单独呈现。用户和 Agent 通过同一领域负责方读取状态、调用当前可用操作并回读结果。重新打开界面继续观察已有工作；当前对话工作区内可定位的产物可以直接预览，媒体审看还能按镜头时码定位。关闭界面只结束这次查看，持续任务仍可在原有工作线上继续。

不同工作采用适合自己的呈现方式：进度、产物、列表和审阅优先复用共享视图；邮件编辑等高密度交互保留专用 MCP App；专业创作、设备控制和持续监测保留专业应用。宿主提供一致的主题、语言、视口和交互入口，领域布局由实际工作决定。外部服务连接与授权统一归口 OPL Connect，消费者身份由可信宿主依据已安装能力绑定；共享工作台的页面选择只承担导航。凭证由服务提供方或原生载体保存和续期，领域操作通过原有负责方使用连接。

共同基座还应让应用使用用户已经维护的知识。产品方法、用户或团队约束、长期主题和具体项目各有归属，内容的性质与有效期独立管理。Obsidian 或普通目录可以继续保存唯一可编辑正文；没有个人资料库时，工作区即可承载。任务按需要读取获准内容并记录当次版本，新的认识经过审阅后写回原处。这样，换一个应用不必重新解释相同的背景，个人信息也不必在多个应用之间各存一份。知道用户偏好与获得操作授权仍是两件独立的事。

这一共同开发方向由 [OPL Agent 原生应用标准](https://github.com/gaofeng21cn/one-person-lab/blob/main/docs/policies/agent-native-app-policy.md) 统一维护。App 聚焦发现、交接和协作体验；连接、知识与领域操作的可用范围，由各自负责方的实际交付和验收确定。

## 清楚分工如何保持体验一致

OPL App 通过清楚分工建立专业性：

```text
OPL 产品体验
  = OPL Base：阶段运行、恢复、证据与交接
  + OPL Packages 与开放插件：专业能力、领域判断、审阅与交付
  + OPL App：极薄底座、入口、交互秩序、状态与下一步
  + OPL Cloud：在线 Workspace、托管资源与组织治理
```

App 负责底座秩序、入口、交互、状态翻译和下一步；Framework 负责运行事实；MAS、MAG、RCA、OBF 或 OMA 等专业智能体负责领域质量判断；云端管理面负责账号、资源和组织策略。新增或升级能力时，用户已有的项目、工作方式和权限边界继续有效；只有经过兼容性、安装、安全和发布验证的变化才会进入正式产品。

清楚边界直接建立用户信任：跨界面的状态保持一致，专业结论按权威路径给出，资源和权限变化始终经过用户知情与授权，显示结果永远不取代运行事实和专业结论。

## 结语

OPL App 希望让一个人拥有类似专业团队的工作界面，并让复杂系统保持易于理解和持续演进。

它让用户从真实目的开始，让成果带着来路，让状态指向下一步，让设置围绕用户决策组织；它以极薄稳定的底座承载来源平权的插件生态与静默自愈演进，让开放扩展始终守住一致体验；它让工作从本机自然延伸到浏览器和 Cloud，同时清楚区分设计目标与发布事实；它把专业能力放进可扩展的 Packages 与开放生态，让 Base、App、Packages 和 Cloud 各自承担清楚而互补的责任。

产品把复杂性放在正确的位置：用户看到目标、成果和决定，专业 Agent 保留判断权，运行系统保留事实，诊断细节在需要时出现。OPL App 的一致性与可靠性，应由这些可观察、可复查的结果持续证明。
