# 软件中心

Owner: `one-person-lab-app`
State: `active`
Machine contract: [`pages.app_management`](../../../contracts/app-gui-product-contract.json)

软件中心让用户直接回答四个问题：有哪些软件、如何开始使用、已经装了什么、哪些可以更新。
MiniApp 的管理与工作入口按
[MiniApp 管理与工作台](miniapp-management.md) 分层：软件管理投影 Package 的安装、
更新、启停与诊断；工作入口再从当前 thread 的 fresh Codex MCP catalog 发现可调用的
`server + resourceUri`。管理界面不维护固定 MiniApp 清单，也不把第三方 connector
surface 计入 OPL 自有 MiniApp 数量。
它管理本机独立安装的软件，包括标准与非标准智能体、Agent 原生应用、本机桌面/Web
应用、命令行工具及独立能力包。OPL 核心是其中一组产品与依赖关系，不是目录范围上限。
云端、移动端和设备端产品拥有独立生命周期；OPL App 可以协助部署、查看远端状态和
打开原产品入口，但它们不进入本机软件安装清单。

## 统一使用路径

顶层入口统一称“软件中心”，日常分区为“软件、更新、共享资源”。软件源与运行组件从管理入口或详情进入。对话与任务负责实际工作；MiniApp 是产品的工作界面，沿用当前任务与产品身份。

可用软件的主要动作是“开始使用”，只选择 owner 声明的任务或界面入口，不自动执行任务。未安装时先安装；需要资料或账户时转到同一共享资源页。保留待使用的产品，安装或授权完成并重新读取后可以继续使用。更新可用是独立信息，不阻断当前可用入口。

共享资源有唯一管理面，软件详情展示已授权的资料与连接并链接到它；设置保留导航与宿主配置，不复制连接管理器。选择资料库使用原生文件夹选择器（可用时），知识范围采用可读选项和 owner 默认值。已有连接不自动授权给新软件。任务记录仍归任务，长期知识沿用既有提议、审阅、写回流程。

“需要你处理”按 owner 提供的共同原因合并，例如同一软件源失去授权影响多个产品只显示一件事项。每件事项显示影响范围、原因和恢复入口。只读刷新与检查复用已有生命周期；未知状态、未使用的可选资源和普通更新不作为故障。处理结果重新读取，不在 UI 中猜测恢复成功。

软件详情首先显示当前使用版本、发布版或开发版、实际位置；其他安装和交付选项逐层展开。解除开发接入保留源码与资料，卸载只作用于确认的安装，数据处理遵循 owner 合同。

## 管理范围

默认打开 **OPL 软件**。同一范围使用一张列表，产品类型作为筛选条件；公开与私有
软件共享目录、交互和管理规则，私有条目的可见性与下载能力由当前授权决定。

| 范围 | 包含什么 | 管理方式 |
| --- | --- | --- |
| OPL 软件 | 我们独立维护的智能体、应用和能力包 | 从同一个 OPL 目录发现，按软件的实际安装器执行安装、更新、卸载 |
| 其他来源 | 外部 Codex 插件、独立 Skill，以及其他渠道的软件；维护归属尚未确认的条目也在这里 | 按来源和实际管理器展示，通过对应的管理入口操作 |
| 运行组件 | 有明确依赖关系、由所属产品维护的运行时或内嵌组件 | 查看被谁使用、由谁维护，随所属产品或依赖管理器更新 |

维护归属来自 Framework 的 `catalog_origin`、`origin_basis` 和 `catalog_source`。
App 不根据名称、ID 前缀或 `publisher` 文本猜测 OPL 身份。归属不授予安全信任、下载
权限或管理权限；可执行动作仍由相应 owner 提供。

PDF、Documents 等 Codex 可选扩展属于“其他来源”。随 Codex 分发只说明交付方式，
不能据此将它们认定为 OPL 运行依赖。独立 Skill 与插件分别展示；插件清单不冒充完整
Skill 清单，当前宿主未提供的管理能力转到已有入口。由 Codex 安装的 OPL 软件仍属于
OPL 软件，安装器不会改变维护归属。

概念仓、文档仓、来源集合和未接入的源码 checkout 不作为可安装软件。本机独立软件缺少安装适配时记录具体缺口；远端产品属于部署目标，不以缺少适配为理由加入本机目录。

## 默认列表

| 列 | 用户看到的内容 |
| --- | --- |
| 软件 | 正式名称与简短用途说明 |
| 类型 | 应用、智能体、能力包；未知时保持待确认 |
| 已装版本 | 当前激活实例的版本；没有激活实例时明确显示未激活 |
| 可用版本 | 当前更新轨道的精确目标，首次安装默认推荐发布版；暂无目标用“—”，详情说明原因 |
| 状态 | 未安装、已安装、可更新、需处理、待检查 |
| 操作 | 开始使用；尚未可用时显示安装、配置或修复入口，更新独立呈现 |

用户按“全部、已安装、可更新、未安装”查找软件，也可以搜索名称和筛选产品类型。
统计按软件身份去重，同一软件的多个安装方式或副本不会增加软件数。开发接入属于
已安装的子集，通过“开发接入”标签和详情表达，不再形成与已安装互斥的统计。
其他来源和运行组件有各自统计，不计入默认 OPL 软件总数或 OPL 更新数。

安装、是否启用和业务可用性是不同事实。列表只呈现当前最重要的状态；启停、权限、
依赖与诊断放在详情。可更新必须有 owner 的更新判定，存在更新按钮或版本字符串
不同都不足以证明有更新。来源版本落后于本机版本时，不提示降级；“已安装”也不
自动表示已检查且为最新版。检查失败保留此前信息并标明当前状态未确认。

软件安装、更新、修复和卸载集中在软件中心。旧智能体与扩展目录深链仍可进入该页；
Settings 的能力配置保留独立 Skills、MCP 与连接的原生配置，提供软件中心入口，
不再重复渲染 Package 清单。设置中的更新入口跳到软件中心的更新分区。
软件详情继续管理首页入口、启停和配置；这些动作使用同一 owner 与回读。

安装的普通入口是目录行中的“安装”。清单 URL 导入属于高级操作，不作为添加日常
软件的默认流程。更新与卸载只作用于所选安装实例，操作前后的确认、反馈与回读复用
同一套 owner 动作机制。

## 软件详情

详情集中显示稳定 ID、维护者、来源、安装方式、安装器、本机代码的实际安装路径、版本、
可用操作，以及必要的依赖与故障说明。多份安装分别列出，用户可以明确选择要管理的
那一份；不拼接多个版本当作一个版本，也不取最大的版本号冒充当前有效版本。

OPL Package 统一使用正式不可变 OCI 制品，原生应用与 CLI 使用正式原生安装器。
源码 checkout 只作为显式开发覆盖，不作为普通安装、更新或修复来源。

GitHub Release、源码分支和提交属于来源详情。它们是不同的发布或开发证据，不与
“已安装”“可更新”并列成为软件分类，也不能代替已验证的安装目标。成熟度只采用
发布者明确声明；技术原型和开发中的软件沿用相同管理标准，不自动添加“预览版”。

安装路径由实际安装器管理：macOS App、Homebrew、Codex 插件、uv 工具及 OPL 自有
安装分别保留原生布局。源码、版本缓存和用户数据分开。软件中心统一发现、呈现和
动作入口，复用安装证据，不复制一份会漂移的安装数据库，也不隐式迁移现有目录。

## 多份安装，一个激活实例

同一软件在同一环境中可以保留多份安装，只有一个激活的运行实例。安装回答“代码放在哪里”，激活回答“OPL App 和 Agent 实际使用哪一份”。插件、CLI 和桌面入口若指向同一 runtime，是这份实例的不同入口，不重复计算为多份激活的软件。

软件详情的“本机安装”逐项显示版本、发布版或开发版、实际路径、安装器和激活状态。切换由软件 owner 或原生载体执行，带精确安装身份与当前 revision；结果重新读取。UI 不保存一份独立的激活选择，不按最大版本、最短名称或目录存在猜测当前实例。未知或冲突要显示原因。

默认安装推荐发布版。开发版只在显式接入后可选择激活；源码更新仍由 Git 和开发工具负责。软件中心提供查看、激活、解除接入等 owner 支持的操作，解除接入保留 checkout 与数据。已存在的开发选择保持真实回读，目录刷新不会擅自切换。

发布版、开发源码、用户资料保持独立路径。安装、更新、卸载的确认中写明目标实例和位置，动作只作用于该实例。非激活版本可保留作回退；卸载激活实例前须由 owner 确定后继或停用，不暗中启用另一份代码。

## 一个 OPL 目录，多种交付渠道

OPL 公共 Package 源、授权私有源和 Homebrew tap 是同一个 OPL 软件目录的交付渠道。
软件源用于获取版本，Stable/Nightly 表示更新轨道，Standard/Full 表示安装规格；这些选项不等于本机有多份安装。主列表只给出一个明确的目标，默认使用发布者推荐版本，已选择轨道则沿该轨道更新。详情的“获取其他版本”保留替代选项；软件源页集中连接、检查和刷新来源。
公开与私有的差异不产生另一套软件类型或更新器。

目录由 Framework 汇总 owner 与原生载体投影；App 只展示和派发动作。框架安装记录不
依赖 Homebrew 收据，缺少某个渠道的收据只说明该渠道未持有安装。外部来源继续使用
其原生生命周期，OPL 不接管 Codex、Homebrew 或其他管理器的版本决策。

软件共享的知识、记忆、账号、授权与模型连接集中在“共享资源”。Obsidian 正文和
凭据仍由已有系统持有，软件源只保存必要引用。底层合同见 Framework 的
[软件源规范](https://github.com/gaofeng21cn/one-person-lab/blob/main/docs/specs/software-sources.md)
和 [Package 目录规范](https://github.com/gaofeng21cn/one-person-lab/blob/main/docs/specs/package-directory.md)。

## 验收

同一份真实状态下，OPL 默认列表与统计不包含 PDF 等外部扩展；其他来源可查到这些
扩展及其管理器。真实开发接入计入已安装，多个安装渠道按产品去重。列表只展示简明
版本与状态，详情仍能核对每份安装及对应操作。桌面和窄屏均能完成搜索、筛选、查看
详情及返回，操作失败和未知结果可见。

源码合同、渲染验收、安装后的 App、正式发布分别取证。尚缺的平台适配应记录为
具体缺口，不以静态产品清单或一次截图宣称全部软件已具备完整生命周期管理。

## 图标与运行组件

目录优先使用发布者随不可变版本提供的真实图标。公开图标绑定精确提交；私有图标仅通过已授权资产入口提供，不能向匿名地址试探私有仓库路径。缺图、离线或加载失败时，优先使用由 App 的 `contracts/software-artwork-assets.json` 资产清单生成并随宿主打包的 PNG；仍无图时使用中性位图占位，不生成首字母或拼接字母 Logo。正式名称、用途与入口读取同一产品投影；打包的图标索引是资产投影，不是另一份产品目录。

运行组件复用 `managed_update` 的 `dependency_catalog`，展示实际版本、安装位置、维护方和所属产品。Codex CLI、Temporal、Python、uv 等仅在 owner 已声明依赖并回读时出现；不扫描或接管全机开发环境。系统或用户管理的依赖保留原维护方式，更新入口转到父产品或既有依赖管理器。
