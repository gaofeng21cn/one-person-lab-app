# 软件中心

Owner: `one-person-lab-app`
State: `active`
Machine contract: [`pages.app_management`](../../../contracts/app-gui-product-contract.json)

软件中心让用户直接回答四个问题：有哪些软件、如何开始使用、已经装了什么、哪些可以更新。
MiniApp 的管理与工作入口按
[MiniApp 管理与工作台](miniapp-management.md) 分层：软件管理投影 Package 的安装、
更新、启停与诊断；工作入口再从当前 thread 的 fresh Codex MCP catalog 发现可调用的
`server + resourceUri`。管理界面不维护固定 MiniApp 清单，也不把第三方 connector
surface 计入 OPL 自有 MiniApp 数量。
软件中心管理可在本机使用的软件，包括智能体、本机桌面/Web 应用、效率扩展、连接通道及其依赖。随 App 交付的内置插件和可独立安装的软件使用同一管理入口。
云端、移动端和设备端产品拥有独立生命周期；OPL App 可以协助部署、查看远端状态和
打开原产品入口，但它们不进入本机软件安装清单。

## 统一使用路径

顶层入口统一称“软件中心”，按 OPL 基于 DSH 的全插件化理念组织：区分来源（OPL 软件、其他来源）与是否默认安装，但不把底层打包规格或实现分层强加给用户；理想态与插件 UI/设置接入宪法见 [插件 UI、设置接入与全插件理想态标准](plugin-ui-and-settings-standard.md)。日常分区为“软件、更新、安装记录”，软件源从管理入口进入；运行组件作为清晰独立的视角与软件目录平级切换，不再隐藏在孤立工具栏入口后。对话与任务负责实际工作；MiniApp 是产品的工作界面，沿用当前任务与产品身份。

可用软件的主要动作是“开始使用”，打开 owner 声明的任务或界面入口。配置型插件提供“配置”入口，微信远程从现有远程连接页绑定账号。尚未安装且有权限的软件显示安装动作。需要资料或账户时转到“设置 → 资料与连接”，携带所选软件与资源焦点。完成安装或授权后回读状态，再打开软件。可用更新单独呈现。

资料与连接帮助用户接入已有资料和业务账号，并明确哪些应用可以读取或维护。来源使用 owner 保存的可读名称，支持改名；旧来源缺少名称时使用工作区名称和资料库序号，内部标识只放技术详情。授权列表按真实应用身份归组，展开后分别设置原有领域的读取和维护权限，不因归组扩大授权。列表显示可用条目与待复核数量；检查、断开和历史记录按需展开。

设置中的“资料与连接”是唯一管理面，软件中心只展示资料、账户授权是否齐备和影响范围，并跳转到此设置页；旧 `/apps?section=resources` 深链兼容跳转到设置，不保留配置表单。选择资料库使用原生文件夹选择器（可用时），知识范围采用可读选项和 owner 默认值。已有连接不自动授权给新软件。任务记录仍归任务，长期知识沿用既有提议、审阅、写回流程。

“需要你处理”按 owner 提供的共同原因合并，例如同一软件源失去授权影响多个产品只显示一件事项。每件事项显示影响范围、原因和恢复入口。只读刷新与检查复用已有生命周期；未知状态、未使用的可选资源和普通更新不作为故障。处理结果重新读取，不在 UI 中猜测恢复成功。

软件详情首先显示当前使用版本、发布版或开发版、实际位置；其他安装和交付选项逐层展开。解除开发接入保留源码与资料，卸载只作用于确认的安装，数据处理遵循 owner 合同。

## 管理范围

默认打开 **全部软件**。顶栏可切换 **全部软件 / OPL 软件 / 其他来源 / 运行组件**，产品类型另作筛选。各来源共享目录、更新、安装记录与异常提示入口，采用实际 owner 开放的管理动作。显式的本地开发接入和用户停用沿用各自的保护。

| 范围 | 包含什么 | 管理方式 |
| --- | --- | --- |
| 全部软件（默认） | 各来源的智能体、应用、效率扩展与连接通道 | 共用目录、统计、状态反馈与更新入口 |
| OPL 软件 | OPL 维护的独立软件及 App 内置插件 | 按软件 owner 提供的生命周期管理 |
| 其他来源 | 外部 Codex 扩展、Billion Context 等 DSH 扩展及其他渠道软件 | 通过对应的 Codex、pnpm、Homebrew 等原生管理器执行 |
| 运行组件 | 运行底座、产品依赖及内部组件 | 展示使用关系、维护者和当前状态，按所属产品或依赖管理器更新 |

产品类型使用 owner 提供的 `software_type`，原生插件提供同一类别语义。Framework Package 的维护归属来自 `catalog_origin`、`origin_basis` 和 `catalog_source`。Studio 内置插件的维护归属来自 DSH profile 投影，权限和动作由实际来源、载体及软件 owner 决定。

PDF、Documents 等 Codex 可选扩展属于“其他来源”。随 Codex 分发只说明交付方式，
不能据此将它们认定为 OPL 运行依赖。独立 Skill 与插件分别展示；插件清单不冒充完整
Skill 清单，当前宿主未提供的管理能力转到已有入口。由 Codex 安装的 OPL 软件仍属于
OPL 软件，安装器不会改变维护归属。

概念仓、文档仓、来源集合和未接入的源码 checkout 不作为可安装软件。本机独立软件缺少安装适配时记录具体缺口；远端产品属于部署目标，不以缺少适配为理由加入本机目录。

## 默认列表

| 列 | 用户看到的内容 |
| --- | --- |
| 软件 | 正式名称与简短用途说明 |
| 类型 | 智能体、应用、效率扩展、连接通道。未知时显示待确认 |
| 已装版本 | 当前激活实例的版本；没有激活实例时明确显示未激活 |
| 可用版本 | 当前更新轨道的精确目标，首次安装默认推荐发布版；暂无目标用“—”，详情说明原因 |
| 状态 | 未安装、已安装、可更新、待检查，或精确异常原因（如待重启生效、需连接软件源、安装冲突、安装不完整、需恢复安装），不使用含糊的“需要处理” |
| 操作 | 开始使用或配置；尚未可用时显示安装、检查软件源或恢复安装入口，更新独立呈现 |

用户可按“全部、已安装、可更新、未安装”筛选，也可以搜索名称及筛选产品用途。软件详情展示 DSH、Codex、OCI、Homebrew 等交付载体。
统计与异常聚合覆盖全部软件来源（OPL 与其他来源平等计入总数、已安装与可更新），同一软件的多个安装方式或副本按软件身份去重。开发接入属于
已安装的子集，通过“开发接入”标签和详情表达，不再形成与已安装互斥的统计。
运行组件和零散独立 Skills 不计入软件总数。

安装、是否启用和业务可用性是不同事实。列表只呈现当前最重要的状态；启停、权限、
依赖与诊断放在详情。可更新必须有 owner 的更新判定，存在更新按钮或版本字符串
不同都不足以证明有更新。来源落后于本机版本时保留本机版本。检查失败保留此前信息并标明当前状态未确认。标准版可以联网按需安装独立软件，完整版可以复用随包的离线载荷。两种规格使用同一软件身份、安装动作和配置入口。更新页提供「检查全部更新」与「更新全部」，涵盖软件包、桌面宿主和原生插件。应用扩展组件全部最新时默认收起。等待重启生效时，更新页和顶栏提供统一入口。扩展回退后，更新页显示原因和重新检查入口。

软件安装、更新、修复和卸载集中在软件中心。旧智能体与扩展目录深链仍可进入该页；
Settings 的能力配置保留独立 Skills 与 MCP 的宿主配置，连接与资料库统一在设置的“资料与连接”中管理，
不再重复渲染 Package 清单或连接管理器。设置中的更新入口跳到软件中心的更新分区。
软件详情继续管理首页入口、启停及安装生命周期；用户配置通过统一插件贡献接入设置：远程通道与伴侣连接进入“连接与部署 → 远程连接与网页访问”，服务状态与诊断进入“运行与维护 → 服务状态”，业务界面进入应用工作台。软件详情提供到同一配置页的直达入口。这些动作使用同一 owner 与回读。

安装的普通入口是目录行中的“安装”。清单 URL 导入属于高级操作，不作为添加日常
软件的默认流程。更新与卸载只作用于所选安装实例，操作前后的确认、反馈与回读复用
同一套 owner 动作机制。

## 软件详情

详情集中显示稳定 ID、维护者、来源、安装方式、安装器、本机代码的实际安装路径、版本、
可用操作，以及必要的依赖与故障说明。多份安装分别列出，用户可以明确选择要管理的
那一份；不拼接多个版本当作一个版本，也不取最大的版本号冒充当前有效版本。

OPL Package 使用 owner 声明且通过校验的 OCI 制品、App 插件公开固定载荷或匹配的离线载荷，原生应用与 CLI 使用原生安装器。
源码 checkout 只作为显式开发覆盖，不作为普通安装、更新或修复来源。

GitHub Release、源码分支和提交属于来源详情。它们是不同的发布或开发证据，不与
“已安装”“可更新”并列成为软件分类，也不能代替已验证的安装目标。成熟度只采用
发布者明确声明；技术原型和开发中的软件沿用相同管理标准，不自动添加“预览版”。

安装路径由实际安装器管理：macOS App、Homebrew、Codex 插件、uv 工具及 OPL 自有
安装分别保留原生布局。源码、版本缓存和用户数据分开。软件中心统一发现、呈现和
动作入口，复用安装证据，不复制一份会漂移的安装数据库，也不隐式迁移现有目录。

## 单一运行态与软件源收敛

在 Framework v2 下，软件中心直接消费 `agent_packages`（含 `package_currentness`、`presence.callable` 及安装进度）与软件来源目录，不再维护独立的多安装实例切换 UI（`SoftwareInstallations` / `SoftwareReleaseOptions`）或 Homebrew Tap 原生软件管理（`native_items` / `source_setup`）。安装、更新、启用、停用与卸载均通过 Framework owner 投影的 `available_actions` 执行并回读最新状态；源码 checkout 只通过开发者显式接入表达，不作为可切换的普通多实例来源。

## 一个 OPL 目录，多种交付渠道

官方软件目录 `opl-catalog` 提供可独立刷新的软件元数据。公共源 `public-registry:opl` 与已授权的私有 GitHub Packages 源（`github-packages:<owner>`）在同一个目录与更新流程中展示；Stable/Nightly 表示 App 发布轨道，Standard/Full 表示安装包规格，本机安装状态由 Framework Package 与载体回读。公共源通过 `source_refresh` 刷新目录后单次回读，私有源逐项校验访问权限，不在无凭据时匿名请求私有制品。[OPL 软件目录](https://github.com/gaofeng21cn/opl-catalog)

进入软件中心或刷新目录时，公共目录支持 owner 投影的无确认 `source_refresh` 动作刷新目录索引；私有软件源继续由用户显式触发 `source_check`、`source_configure` 或 `source_disconnect` 管理凭据与权限。公共目录允许展示授权条目的已公开字段；制品下载、安装和更新仍由发布源重新校验权限，未获授权时在软件详情或软件源页引导授权连接。

Framework 汇总 Package 目录与来源投影，Studio 额外提供随 profile 装载的原生插件。App 消费两类投影并派发动作。

应用使用的资料库、业务账号及其授权集中在“设置 → 资料与连接”（`knowledge_source_*` 与 `connection_*`）。模型账号与默认模型留在设置，OPL Link 与消息通道留在远程连接设置，运行组件与工具维护使用既有管理入口。Obsidian 正文和凭据仍由已有系统持有，软件源只保存必要引用。底层合同见 Framework 的
[软件源规范](https://github.com/gaofeng21cn/one-person-lab/blob/main/docs/specs/software-sources.md)
和 [Package 目录规范](https://github.com/gaofeng21cn/one-person-lab/blob/main/docs/specs/package-directory.md)。

## 状态与任务反馈

软件页首屏以搜索、筛选和软件列表为主。页头用一行展示本机目录和读取状态，刷新期间继续显示上次读取的目录。软件或来源有异常时，按需展开原因和对应入口。安装进度与结果在「安装记录」中查看。
“已安装”只表示本机存在安装，“开始使用”还需要当前调用与激活状态允许。

安装确认展示正式名称、目标版本、软件源、发布版或开发版、下载量、缓存、可用空间和
目标位置；标识符放入技术详情。缺少来源或占用信息时保留未知，不猜测数据。

任务展示当前阶段和下一阶段。下载提供实测字节、速度和剩余时间，少于一分钟按秒显示；
校验、解压、安装和结果检查不显示虚构的百分比。取消保留缓存，继续和重试仍经预检查，
校验通过后才能复用。软件行同步显示当前阶段，并禁用重复的生命周期操作。

返回对话后，全局任务入口继续显示进行中或有异常的任务，点击打开软件中心的「安装记录」。
重开界面时从 Framework 恢复任务观察；读取失败保留上次观察，但隐藏过期的速度和百分比。
中断显示“结果待确认”，先检查软件状态。新一次任务取代同软件的旧尝试；进行中和待处理
任务优先展示，最近完成或取消的任务收进记录。完成后仅在最新软件状态允许调用时提供
“开始使用”，安装位置沿同一文件管理器入口查看。

共享来源或资源的问题按明确身份聚合，列出受影响的软件及数量；独立安装冲突仍单独处理。
普通更新不计为故障。状态和恢复动作来自既有 owner，客户端只组织展示与导航。

## 验收

同一份真实状态下，默认「全部软件」视图与统计平等覆盖 OPL 软件、外部插件与 DSH 插件，同时支持按「OPL 软件」「其他来源」「运行组件」切换并保持独立 Skills 与运行组件不混入软件统计。真实开发接入计入已安装，多个安装渠道按产品去重。列表只展示简明版本与状态，详情仍能核对每份安装及对应操作。更新页、桌面托盘与设置关于页均使用准确的人类可读状态与深链跳转，错误、忙时拒绝与无更新情况不返回误导性的成功提示。桌面和窄屏均能完成搜索、筛选、查看详情、触发更新及重启生效。

源码合同、渲染验收、安装后的 App、正式发布分别取证。尚缺的平台适配应记录为
具体缺口，不以静态产品清单或一次截图宣称全部软件已具备完整生命周期管理。

## 图标与运行组件

目录优先使用发布者随不可变版本提供的真实图标。公开图标绑定精确提交；私有图标仅通过已授权资产入口提供，不能向匿名地址试探私有仓库路径。缺图、离线或加载失败时，优先使用由 App 的 `contracts/software-artwork-assets.json` 资产清单生成并随宿主打包的 PNG；仍无图时使用中性位图占位，不生成首字母或拼接字母 Logo。正式名称、用途与入口读取同一产品投影；打包的图标索引是资产投影，不是另一份产品目录。

自有软件的品牌与 README 入口遵循 Framework 的[Agent App 品牌规范](https://github.com/gaofeng21cn/one-person-lab/blob/main/docs/policies/agent-native-app-policy.md#品牌与公开入口)。新图稿先保存于产品 owner 仓库，再同步既有离线资产清单、摘要与 Studio 构建资源；同一产品的 Package 图标与离线图稿保持一致。新增 `opl-image` 继续使用稳定身份，显示为 **OPL Image Lab**，不创建第二个软件条目。

运行组件仅在 owner 声明并回读依赖目录时展示实际版本、安装位置、维护方和所属产品（`managed_update.components` 中的 `opl_base` 在更新页以只读方式展示当前运行版本，不再由宿主触发通用升级或回滚）；不扫描或接管全机开发环境。系统命令行工具与 OPL 托管运行时按各自实际维护者展示，版本检查待完成或组件缺失时直接显示对应状态。

设置由 App 静态定义目的地。资源 owner 或插件声明设置能力、标准 view type、读取与动作引用；Framework 验证并投影，Studio 在统一 App 设置容器中渲染。插件不创建顶层导航，也不复制凭据存储或绕过 App action bridge。知识来源继续由 Framework 的 Profile/Workspace owner 提供，接入不要求另外创建插件。
