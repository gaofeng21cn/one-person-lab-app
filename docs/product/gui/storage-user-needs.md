# 数据管理：用户任务与产品模型

Owner: `one-person-lab-app`
State: `product-design`
Purpose: 从用户任务定义数据管理能力和界面，不以旧版实现、文件目录或现有合同字段作为产品答案。

## 三层产品判断

**产品层：OPL App 是用户完成持续知识工作的工作台。** 用户来这里不是管理
文件目录，而是从一个目标出发，继续任务、查看成果和证据、做出决定，并知道下一步。App
把运行、专业能力和数据 owner 的事实翻译成可行动的用户状态；它不复制这些 owner 的真相。

**能力层：每一个用户目标都必须有真实 owner 的可执行闭环。** App 只能提供 owner
已经声明并能回读的盘点、预览、执行、恢复或导出能力。当前对话由 Codex App Server
持有，已具备归档、恢复和删除协议；项目只是 thread 的 affinity 分组，不是可级联删除的
数据 owner；当前输入附件是 send-scoped 输入，不是 App-owned 附件库。日志和缓存由本地
生命周期 owner 持有。能力缺口优先补 owner 和桥接，不先做 UI 装饰。

**UI 层：最后统一呈现同一条决策链。** 每个可操作状态都要回答“现在是什么、我能做
什么、做完会怎样”，但 UI 不得为没有 owner 的对象发明删除按钮。能力稳定后再统一入口、
信息密度和视觉组织。

## 先回答用户的问题

用户进入“数据与存储”通常不是为了查看目录，而是为了完成下面四件事：

1. **知道空间去了哪里**：哪些内容占空间，统计是否可信，最近一次盘点是什么时候。
2. **释放空间**：希望尽量不影响使用，知道能释放多少，确认后会留下什么。
3. **整理旧内容**：找到不再需要的对话、项目、附件或运行记录，并在删除前保留恢复机会。
4. **确认不会误删**：知道哪些数据重要、哪些数据会影响当前运行，哪些动作可恢复。

因此，页面的第一层不应该暴露文件名、owner 或技术路径，而应该给出一条完整的决策链：

> 当前是什么状态 → 我现在能做什么 → 做完会变成什么状态

## 数据不是一个集合

产品需要按用户能理解的生命周期分组，同时保留真实 owner：

| 用户看到的类别 | 用户关心的问题 | 当前能力判断 | 必须提供的能力 |
| --- | --- | --- | --- |
| 对话与附件 | 哪些内容属于我的工作记录，能否归档、恢复或删除 | 缺口 | 按时间/项目筛选，归档或导出，删除前可恢复，删除后可验证 |
| 项目与工作区 | 删除项目会不会影响正在运行的任务和产物 | 部分具备 | 活跃使用检测，归档后删除，冲突和恢复入口，结果回读 |
| 智能体与运行环境 | 哪些安装内容可移除，移除后还能否运行已有工作流 | 只有 owner 导航和部分用量 | owner 提供依赖影响、预计释放空间、移除后可用性和回滚状态 |
| 网页端数据 | 数据是否存在、存在哪里、谁能清理 | 只读或未测量 | 部署 owner 提供盘点、清理/导出动作和完成后的 host 回读 |
| 缓存与日志 | 清理能释放多少，会不会影响当前使用 | 已有安全清理基础 | 推荐清理、预览、确认、结果回读；明确不可恢复和不影响的范围 |
| 记忆与纠错记录 | 哪些是系统记忆，用户提交的修正是否已生效 | 纠错建议能力已具备 | 区分 canonical 与用户建议，显示处理状态和删除建议的结果 |

“缓存与日志”不能代表全部数据管理；它是低风险释放空间路径，不应让用户误以为对话、项目和附件也已经可以删除。

## 能力层的最小完整闭环

每一类数据都不要求拥有同样的写操作，但必须能返回同一种用户可理解的状态模型：

```text
inventory     当前占用、统计时间、新鲜度、影响范围
recommend     推荐的下一步，以及为什么推荐
preview       选定动作会改变什么、释放多少、会保留什么、是否可恢复
execute       执行一次明确动作，并绑定确认和并发保护
readback      重新盘点实际结果，不能用 receipt 或成功文案代替
restore       对声明可恢复的动作提供恢复入口和冲突决策
```

能力可以由不同 owner 提供，但不能只暴露一个技术动作名。每个动作至少需要：

- `user_goal`：用户在解决什么问题，例如 `release_space`、`organize_old_data`；
- `current_state`：动作前的可验证状态；
- `expected_state`：动作成功后用户会看到的状态；
- `impact`：会影响哪些功能、哪些数据明确不会改变；
- `recoverability`：`restorable`、`not_restorable` 或 `owner_defined`；
- `freshness`：盘点时间和是否仍可作为确认依据；
- `next_step`：当前最适合用户执行的一个动作。

没有这些字段时，App 只能展示“有一个清理按钮”，不能让用户预测结果。

## 页面信息架构

### 第一屏：总览和下一步

第一屏只回答三个问题：

- **已确认占用**：已盘点的数据总量；未知数据单独显示为“未统计”，不能显示为 `0 B`。
- **现在可安全释放**：当前盘点可回收的空间，以及是否需要确认。
- **需要我决定的内容**：例如“有一组旧项目可归档”，而不是列出所有文件。

主按钮只表达用户目标，例如“释放 1.2 GB”，旁边说明“只包含缓存和旧日志，不影响对话、项目和当前任务”。

### 第二层：按任务分组

1. **释放空间**：默认勾选安全推荐项；用户可以展开明细再调整。显示释放前、预计释放后、不可恢复提示。
2. **整理我的内容**：对话、项目、附件以用户对象呈现，不暴露路径。当前没有 owner 能力时显示“暂不支持删除，但可前往所属页面查看”，不能渲染伪按钮。
3. **保护中的数据**：列出当前被保留的类别和原因，例如“正在运行的会话”“工作区产物”“凭据”。这不是可操作列表，而是降低误删焦虑的解释。
4. **技术详情**：路径、owner、扫描耗时、receipt 和原始标识放在折叠区域，供排障使用。

每个可操作行都采用同一结构：

```text
当前状态：已盘点 / 未盘点 / 过期 / 部署方未提供
动作：释放、归档、导出、恢复、重新盘点
预期结果：释放 X、保留 Y、影响范围、是否可恢复
```

### 操作反馈

- **预览**：展示明确的 before/after，而不是只显示 plan id。
- **确认**：确认文案使用用户目标，例如“释放空间”，并列出不会改变的内容。
- **执行中**：锁定同一数据集，显示正在处理的范围。
- **完成**：重新盘点并显示实际释放量、剩余量、未完成项和恢复入口。
- **失败或部分成功**：保留已完成结果，说明剩余动作，不把部分成功显示成全量成功。

## 当前实现的产品缺口

### 已经可以交付的部分

- owner 声明的日志和缓存可以盘点；
- 只选择超过保留期且未发生变化的文件；
- 预览后确认，执行时校验文件指纹；
- 工作区、产物、凭据、会话和记忆受到保护；
- 执行后生成 receipt，能证明删除了哪些文件。

### 仍然缺失的部分

1. **没有统一的存储总览**：App 投影的 Agent/WebUI 用量和 Workbench 日志/cache 清理是两套页面、两套统计。
2. **没有“推荐”能力**：用户需要自己逐个勾选文件，系统没有回答“现在最值得做什么”。
3. **预览没有完整表达预期状态**：已有 selected/retained bytes，但 UI 没有用 before/after 和影响范围做用户确认。
4. **没有用户数据整理闭环**：对话、项目、附件和会话没有归档、导出、恢复和删除后的 readback。
5. **没有恢复策略**：当前日志/cache 清理不可恢复，必须在确认前明确显示；可恢复的数据类别还没有 owner contract。
6. **完成状态没有绑定重新盘点**：receipt 只能证明一次执行，不能证明用户现在实际剩余多少空间。
7. **未测量和不可用状态缺少下一步**：部署方未提供数据时要说明责任边界和去哪里操作，而不是只显示“不可用”。

## 实施优先级

### P0：让现有安全清理成为可预测的用户路径

- 统一 Storage 页面总览和 Workbench inventory；
- 从“文件列表”改为“推荐释放空间”并支持展开明细；
- 预览和完成回读显示 before/after、影响范围和可恢复性；
- 对未盘点、过期、未提供和失败状态给出下一步；
- 不扩大清理边界，不把受保护数据伪装成可操作。

### P1：补齐用户内容整理

- 以对话、项目、附件为对象的 inventory；
- 归档/导出优先于删除；
- 删除前检查活跃任务和依赖，生成可恢复 receipt；
- 删除后 readback，恢复时处理名称或 id 冲突。

### P2：补齐 owner 能力和跨部署一致性

- Agent/Package owner 返回移除影响和释放空间；
- WebUI/deployment owner 提供 host 侧盘点和清理入口；
- runtime generation、更新缓存和安装缓存分别声明生命周期，不混用“清理”。

## 验收标准

从用户视角，以下问题必须能在页面上直接回答：

1. 我现在知道哪些数据被统计了，统计是什么时候完成的。
2. 我能看到一个推荐动作，以及它为什么安全、会释放多少。
3. 点击确认前，我知道哪些内容会变、哪些内容不会变、能否恢复。
4. 点击完成后，我看到实际释放量和新的盘点结果，而不是只有一个 receipt 编号。
5. 对话、项目、附件尚未支持删除时，页面明确说明“暂不支持”，不会用清理缓存的按钮制造错觉。
