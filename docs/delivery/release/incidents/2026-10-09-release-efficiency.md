## Follow-through improvements

Full's preparation caller passed neither a dependency manifest nor a build cohort. The reusable job therefore skipped preparation even though its VM caller had a prepared-artifact input. In final VM job [113871657113](https://github.com/gaofeng21cn/one-person-lab-app/actions/runs/37945190366/job/113871657113), cache restoration downloaded **525,246,281 bytes** (about 501 MiB) and took approximately **204 seconds**. The log showed continuous transfer, so the delay was observable work, not proof of a stuck process.

The caller now supplies the actual Full build cohort after a fresh build, or its original producer run on checkpoint recovery. Preparation runs alongside hosted qualification, checks the frozen tarball hashes and exposes an artifact name only after upload succeeds. The reusable workflow has explicit read-only Actions permission for cross-run cohort download. VM preparation failure retains the existing online/digest-checked fallback. Cache entries now contain only the two required tarballs in a new cataloged namespace, leaving npm's duplicate cache content out of repeated transport. Existing offline-reuse and corrupt-tarball tests continue to exercise the real prefetch script; no network result or digest is fabricated.

The official dispatch CLI now exercises the scope validator from the selected immutable verification App before dispatch. The VM input check remains in place for direct workflow callers. The finite paired-test map now includes Stable clean-VM, smoke and upgrade tests; unlisted tests and runtime paths remain forbidden. The compatibility regression executes both an old consumer policy and the current consumer, so a controller-side pass alone is insufficient.

Studio's root-package readiness wait now stops immediately when the current App PID's first-install record becomes `failed`, rather than waiting out the 900-second budget. A complete owner projection still succeeds; running, missing or stale records retain bounded convergence behavior. Subsequent Codex/refresh checks run only after Framework readiness succeeds. The current-PID reader remains the existing VM bridge; no second installation-status owner was added.

Incident status previously recognized legacy `stage`/`timestamp` events but missed Studio's `[opl-studio-clean-vm]` JSON `phase`/`at` events. It now accepts raw runner stderr and Actions-prefixed Studio events, including clone, start and guest-IP markers, while retaining heartbeat exclusion and unknown-VM behavior when no runtime evidence exists. This closes the observation gap without adding polling infrastructure or interpreting job names as allocation proof.

## Validation and remaining costs

Post-release validation covers frozen Full preparation wiring, successful prepared transport and fallback, exact offline hashes, corrupted tarballs, old/current consumer compatibility, forbidden paths, terminal installation failure, and both raw and Actions-prefixed runtime markers. The strict release typecheck and active-shell contract/candidate conformance passed. The release-boundary run covered 1,484 tests: 1,474 passed, eight were already skipped by their declared conditions, and two old workflow assertions needed updating for the new frozen-input route. Those two affected cases passed on the focused rerun, leaving 1,476 passing cases and no unresolved failures. Studio's focused qualification/readiness suite passed 30 cases; the current-PID preview regression passed separately. Passed unaffected gates were not repeated. No additional product release or local App replacement is triggered by these changes.

Full production job `113829436590` measured 803.424 seconds for package construction, including 169.753 seconds of Shell build and 533.657 seconds of aggregate packaging/compression. The inner `full_dmg_compression` subprocess took 374.529 seconds. These nested timings must not be added together. Signing, notarization, exact artifact transport, ordinary-account clean-VM and public readback remain required costs. The next real release will measure whether the preparation and smaller cache reduce end-to-end time; local passing tests do not establish that production timing yet.

General operating rules are maintained in the [Stable release SOP](../stable-release-sop.md), rather than a second release controller. The [previous efficiency review](2026-10-08-release-efficiency.md) remains the historical baseline for strict pre-build typechecking and prepared-first VM restoration.
